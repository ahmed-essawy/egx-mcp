# Research: Search and AI discoverability

All web facts checked on 2026-10-31. Code facts checked in the workspace at BASE `6683d29` plus the uncommitted spec 007 work in the same folder (see plan.md, Preconditions).

## R1. Crawler rules and named crawlers

- **Decision**: `/robots.txt` has one `User-agent: *` group and one named group that lists every named crawler on its own `User-agent` line. Both groups carry the same rules: `Allow: /`, `Allow: /mcp/server-card`, then `Disallow:` for `/dashboard`, `/authorize`, `/callback/`, `/token`, `/register`, `/mcp`. Last line `Sitemap: <origin>/sitemap.xml`. The named list lives in one constant (`CRAWLERS` in `src/site/crawl.ts`):
  - Search: `Googlebot`, `Bingbot`, `Applebot`, `DuckDuckBot`, `YandexBot`, `Amzn-SearchBot`
  - AI answer and search: `OAI-SearchBot`, `Claude-SearchBot`, `PerplexityBot`, `DuckAssistBot`, `GoogleOther`
  - AI training and control tokens: `GPTBot`, `ClaudeBot`, `Google-Extended`, `Applebot-Extended`, `CCBot`, `Meta-ExternalAgent`, `Amazonbot`, `Bytespider`, `cohere-ai`, `MistralAI-Training`
  - User-triggered fetchers: `ChatGPT-User`, `Claude-User`, `Perplexity-User`, `Meta-ExternalFetcher`, `MistralAI-User`, `Amzn-User`
- **Rationale**: Google's robots.txt rules say a crawler uses only the most specific matching group and named groups are not merged with `*`, so the named group must repeat every `Disallow` (developers.google.com/search/docs/crawling-indexing/robots/robots_txt). Several `User-agent` lines may share one group (RFC 9309), which keeps one copy of the rules. Training crawlers are allowed (owner decision, spec Clarifications). Tokens are from the vendors' own pages: OpenAI developers.openai.com/api/docs/bots, Anthropic support.claude.com/en/articles/8896518, Perplexity docs.perplexity.ai/guides/bots, Google developers.google.com/crawling/docs/crawlers-fetchers/google-common-crawlers, Apple support.apple.com/en-us/119829, Amazon developer.amazon.com/amazonbot, Meta developers.facebook.com/docs/sharing/webmasters/web-crawlers, Common Crawl commoncrawl.org/ccbot, DuckDuckGo duckduckgo.com/duckduckgo-help-pages/results/duckassistbot, Mistral docs.mistral.ai/en/robots. `Bytespider` and `cohere-ai` have no official page; they are listed so the rules state the allow explicitly (spec FR-S01), which costs nothing.
- **Note**: user fetchers (`ChatGPT-User`, `Perplexity-User`, `Meta-ExternalFetcher`, `Amzn-User`) may ignore robots.txt; private pages are therefore also protected by `noindex` and by needing a session, not by robots.txt alone.
- **Note on Disallow plus noindex**: a URL blocked in robots.txt can still be listed without content if it is linked (the home page links to `/dashboard`). The spec requires both the exclusion and the `noindex` signal (FR-S01, FR-S04), so both are kept; the crawler that obeys robots.txt never fetches the private page, and anything that fetches it sees `X-Robots-Tag: noindex, nofollow`.
- **Alternatives**: one group per crawler (25 copies of the same rules, harder to read and to test); relying on `*` only (spec FR-S01 requires explicit names).

## R2. Sitemap and hreflang

- **Decision**: `/sitemap.xml`, `application/xml; charset=utf-8`, `urlset` with `xmlns:xhtml`. One `<url>` per public HTML page at its canonical URL with `<lastmod>` equal to the page's `updated` date. Pages with a translation carry `xhtml:link rel="alternate"` for `en`, `ar` and `x-default` (the English page) in each of the two `<url>` entries. No `.md`, text or image URLs. Language codes `en` and `ar` (no region).
- **Rationale**: Google's localized versions guide: links must be reciprocal, each version lists itself and the others, `x-default` is the fallback, sitemap form uses `xhtml:link`; `ar` is valid ISO 639-1 and the content is not Egypt-only wording (developers.google.com/search/docs/specialty/international/localized-versions). `<changefreq>` and `<priority>` are ignored by Google, so they are left out.
- **Alternatives**: hreflang only in HTML (the spec asks for sitemap alternates, FR-S02); a sitemap index (one file of 14 URLs is far under the 50,000 limit).

## R3. llms.txt, llms-full.txt and plain-text pages

- **Decision**:
  - `/llms.txt`: Markdown following llmstxt.org: H1 `EGX MCP`, blockquote with the one-sentence description, a short paragraph (who it is for, server address, transport, sign-in methods, data limits, last updated), H2 `Pages` (every English content page as `[title](md url): description`), H2 `Tools` (every tool, `name: description`), H2 `Arabic` (Arabic pages, once released), H2 `Optional` (privacy, terms, the full-content file, the discovery file). Served as `text/plain; charset=utf-8`.
  - `/llms-full.txt`: the same header, then the full Markdown of every English and Arabic content page in page-set order, separated by `---`, then the privacy and terms pages as links with their description only (see plan.md, Spec changes: the legal text names a person).
  - Plain-text pages: every public HTML page has a Markdown twin at `<path>.md` (home is `/index.md`, Arabic home `/ar.md`), served as `text/markdown; charset=utf-8`, and the HTML URL serves the same Markdown when the request's `Accept` header prefers `text/markdown` or `text/plain` over `text/html`. Each HTML page advertises its twin with `<link rel="alternate" type="text/markdown" href="...">` and the HTTP `Link` header; the twin answers with `Link: <html url>; rel="canonical"`.
- **Rationale**: llmstxt.org (spec page modified 2026-08-10) defines the H1, blockquote, file-list sections and the `Optional` section, and the `.md` twin convention (`page.md`, `index.md` for directory URLs) with `rel="alternate" type="text/markdown"`. llms-full.txt is a de facto convention (Mintlify, co-developed with Anthropic). No major crawler officially documents reading llms.txt and Google says it does not use it; agents and tools that fetch pages do read Markdown, and the cost is a few routes with no I/O. The spec wants plain-text twins reachable both by address and by type (FR-S21), so both are served; `Vary: Accept` keeps caches correct. The canonical `Link` header keeps search engines from indexing the twin as a duplicate (Google supports `rel="canonical"` in HTTP headers).
- **Alternatives**: `index.html.md` naming (our URLs have no `.html`, so `page.md` is the matching form); `text/markdown` for llms.txt (the spec names no type and `text/plain` displays in every browser and fetcher).

## R4. MCP discovery files

- **Decision**: three discovery responses, all built from one `serverCard(ctx)`:
  1. `GET /mcp/server-card`: SEP-2127 Server Card, `application/mcp-server-card+json`. Fields: `$schema` `https://static.modelcontextprotocol.io/schemas/v1/server-card.schema.json`, `name` `io.github.ahmed-essawy/egx-mcp`, `version` (the `SERVER_VERSION` of `src/mcp/server.ts`), `title` `EGX MCP`, `description` (registry description, 100 chars or fewer), `websiteUrl`, `repository` `{ url, source: "github" }`, `icons` (the existing `mcpIcons(origin)`), `remotes: [{ type: "streamable-http", url: <origin>/mcp, headers: [Authorization, optional, secret] }]`, `_meta` with namespaced keys `io.github.ahmed-essawy/auth` (OAuth metadata URL, API key header form, dashboard URL) and `io.github.ahmed-essawy/tools` (name and description of every tool) and `io.github.ahmed-essawy/data-notice`.
  2. `GET /.well-known/ai-catalog.json`: AI Catalog, `application/ai-catalog+json`: `{ "specVersion": "1.0", "entries": [{ "identifier": "urn:air:egx-mcp:mcp:egx-mcp", "type": "application/mcp-server-card+json", "data": <the card> }] }`. An entry holds exactly one of `url` or `data`; `data` with the full card inline is chosen. The well-known file therefore carries the address, transport, sign-in methods, name, description, icons and tool list in one fetch (spec FR-S22 "at the well-known location").
  3. Both carry the CORS headers the SEP requires (`Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods: GET`, `Access-Control-Allow-Headers: Content-Type, If-None-Match`, `Access-Control-Expose-Headers: ETag`) and `Cache-Control: public, max-age=3600` with an `ETag`, answering `304` to a matching `If-None-Match`.
- **Rationale**: SEP-2127 "MCP Server Cards" is Final on the Extensions Track (modelcontextprotocol.io/seps/2127-mcp-server-cards.md). Its discovery doc (github.com/modelcontextprotocol/experimental-ext-server-card/blob/main/docs/discovery.md) recommends `<streamable-http-url>/server-card` and `/.well-known/ai-catalog.json`, and lists `/.well-known/mcp/server-card` as not recommended. The card schema has no tools field ("cards do not enumerate primitives"), so the tool list goes in `_meta` under a reverse-DNS key (prefixes ending in `mcp` or `modelcontextprotocol` are reserved, ours is not). The card `name` must have exactly one slash, which the registry name `io.github.ahmed-essawy/egx-mcp` has.
- **Routing fact (checked in `node_modules/@cloudflare/workers-oauth-provider/dist/oauth-provider.js` 1.2.4, `matchApiRoute`)**: the provider treats `/mcp` and every `/mcp/...` path as the protected API route, so `GET /mcp/server-card` would get `401`. `src/index.ts` therefore answers `GET` and `HEAD` `/mcp/server-card` before the guard and the provider. The provider intercepts only `/.well-known/oauth-authorization-server` and paths under `/.well-known/oauth-protected-resource`; `/.well-known/ai-catalog.json` reaches `defaultHandler` unchanged.
- **Alternatives**: Smithery's static card at `/.well-known/mcp/server-card.json` (SEP-1649 shape with `serverInfo` and full tool schemas; our input schemas live in private SDK state, and Smithery uses it only when its scan fails; recorded in the listing kit as an owner follow-up); serving only the catalog with `url` (then a client probing the MCP URL finds nothing).

Namespace: GitHub login grants `io.github.<user>/*`; domain namespaces need DNS TXT or `/.well-known/mcp-registry-auth` on the exact host, and DNS is impossible on workers.dev (modelcontextprotocol.io/registry/authentication). ## R6. Structured data

- **Decision**: one `<script type="application/ld+json">` per public page holding an `@graph`:
  - Home: `Organization` (`@id` `<origin>/#organization`, `name`, `url`, `logo` the 512 px icon, `sameAs` the repository, `contactPoint` `{ contactType: "customer support", url: issues page }`), `WebSite` (`@id` `<origin>/#website`, `name` `EGX MCP`, `url` `<origin>/`, `inLanguage`, `publisher` the organization), `SoftwareApplication` (`name`, `description`, `url`, `image`, `applicationCategory` `FinanceApplication`, `operatingSystem` `Any`, `offers` `{ price: "0", priceCurrency: "USD" }`, `publisher`), and the `WebPage`.
  - Every other page: `WebPage` (`url`, `name` = title, `description`, `inLanguage`, `dateModified`, `isPartOf` the website, `breadcrumb`) and `BreadcrumbList` (Home, then the page; the last item has no `item` URL is allowed but we give it for clarity).
  - Questions page: `FAQPage` with `mainEntity` of `Question` and `acceptedAnswer` `Answer` whose `name` and `text` equal the visible question and answer text exactly.
  - Each connection guide: `HowTo` with `name` (the visible steps heading) and `step` of `HowToStep` with `position`, `name` and `text` equal to the visible step text.
- **Rationale**: Google deprecated FAQPage rich results on 2026-05-08 and removed HowTo documentation in 2023 (developers.google.com/search/updates). They stay valid schema.org types, the spec requires them (FR-S08), they restate visible text only, and assistants and other engines parse them; they are emitted for meaning, not for a Google rich result. `WebSite` with `name` and `url` on the root home page is what Google uses for the site name (developers.google.com/search/docs/appearance/site-names). `Organization` has no required properties; the logo must be at least 112 px (the 512 px icon). `BreadcrumbList` needs at least two items. SoftwareApplication rich results require `aggregateRating` or `review`, which this service cannot truthfully provide, so Google's Rich Results Test will mark that item not eligible; schema.org validation still passes. SC-003 is worded accordingly (plan.md, Spec changes).
- **CSP**: a `<script>` whose `type` is not a JavaScript MIME type is a data block that the HTML parser never executes; the "prepare the script element" algorithm returns at the data-block step before the CSP check (html.spec.whatwg.org/multipage/scripting.html#prepare-the-script-element; MDN script type). `default-src 'self'` therefore needs no change. The JSON is serialized with `<`, `>` and `&` escaped as `\u003c`, `\u003e`, `\u0026` so it cannot close the element.
- **Alternatives**: microdata in the HTML (more markup in every element, harder to test equality); dropping FAQPage and HowTo (spec FR-S08 asks for them; no cost).

## R7. Hosting, caching and the free tier

- **Facts** (developers.cloudflare.com/workers/platform/limits, /workers/reference/how-the-cache-works, /workers/runtime-apis/cache, /workers/platform/pricing, /workers/cache): 100,000 requests per day on the Free plan, refused with error 1027 past it (not billed); 10 ms CPU per request. A Worker runs before the CDN cache and `Cache-Control` does not make Cloudflare cache a Worker response. The Cache API (`caches.default`) has no effect on `*.workers.dev`. The opt-in Workers Caching (`"cache": { "enabled": true }`) works on workers.dev, but hits still count as requests. A fresh browser cache hit never reaches the Worker; a `304` revalidation does and counts.
- **Decision**: render public responses in the Worker from the source module (no I/O), with `Cache-Control: public, max-age=3600` on pages and text files and `public, max-age=86400` on the preview image, a strong `ETag` (first 32 hex chars of the SHA-256 of the body) and `304` on a matching `If-None-Match`. No Cache API, no Workers Caching, no static assets in this feature.
- **Rationale**: the browser cache removes repeat human requests; crawlers revalidate cheaply; CPU per page is far under 10 ms (string building plus one SHA-256 of under 100 KB). Requests stay within budget at 10 times today's traffic (plan.md, Free-tier budget). Workers Caching would only save CPU, which is not the binding limit, and would add a `wrangler.jsonc` change that caches every route unless carefully scoped.
- **Alternative kept for later**: Workers static assets are free and do not count against the request quota. Moving public pages there needs generated files committed or a build step, a `_headers` file for the CSP, and loses `Accept` negotiation (spec 005 recorded the same trade-off). Trigger to revisit: public requests above 20,000 per day in the Cloudflare dashboard, or any day the account reaches 70,000 requests.

## R8. Change notification (IndexNow)

- **Decision**: serve the IndexNow key file at `/c60c57998197b5e5b4a9fc2f935a3c44.txt` (body: the key, `text/plain; charset=utf-8`); the key is a constant in `src/site/identity.ts`. Submission is an owner command after each deploy that changes pages (quickstart.md, IndexNow), POSTing the sitemap URLs to `https://api.indexnow.org/indexnow`. No cron, no Worker subrequest.
- **Rationale**: IndexNow is free and shared by Bing, Yandex, Seznam, Naver, Yep and Amazon (indexnow.org/faq); the key is public by design; a key file at the root covers the whole host (indexnow.org/documentation). Google does not use IndexNow; Google is notified through the sitemap in Search Console (owner task). A Worker that pings on deploy would need a trigger the free setup does not have, and a cron ping would repeat without change.
- **Alternatives**: a scheduled ping (violates "no scheduled job beyond the free limits" in spirit and pings without changes); the deprecated Google sitemap ping endpoint (retired by Google in 2023).

## R11. Tool catalog single source

- **Decision**: move each tool's description string into a new `src/mcp/tool-descriptions.ts` (`TOOL_DESCRIPTIONS`, typed `Readonly<Record<ToolName, string>>`). `ToolDefinition` drops its `description` field and `defineTool` reads `TOOL_DESCRIPTIONS[tool.name]`. The site catalog adds per-tool examples and returns in `src/site/tool-catalog.ts`, typed `Record<ToolName, ...>` so a new tool without catalog text fails the typecheck. A Node-pool test lists the tools of a real `createServer` (`listNodeTools`) and asserts names and descriptions equal the catalog, the summary files and the server card.
- **Rationale**: the SDK keeps registered tools in a private field (`private _registeredTools` in `@modelcontextprotocol/server` 2.3.1), so the site cannot read them at runtime without running an MCP session; a shared constant is the one source both read (FR-S28), and the test proves the registered output equals it. Three descriptions use limits (`MAX_ITEMS_PER_USER` from `src/store/d1/personal.ts`, `MAX_SINCE_AGE_DAYS` from `src/mcp/tools/personal.ts`); the first is imported, the second moves to `src/store/d1/events.ts` beside `DEFAULT_EVENTS_LIMIT` (it bounds the events query window) to avoid an import cycle.
- **Alternatives**: copying descriptions into the site with an equality test (two sources, against FR-S28); building the catalog at runtime by calling `tools/list` on an in-memory server (spins the MCP stack for a web page).

## R12. Freshness without a build step

- **Decision**: each page record carries `updated: "YYYY-MM-DD"`. A test (`tests/unit/site-freshness.test.ts`) pins, per page path, the `updated` date and the SHA-256 of the page's content model rendered for a fixed test origin and the `wrangler.jsonc` limits. Changing any visible text changes the hash, the test fails with the new hash in its message, and the change must bump `updated` and the pin together. Summary files and the server card use the newest page date. Workers Builds deploys the source as committed, so the dates do not move on deploy and are the same on every isolate.
- **Rationale**: no build step exists (`npm run deploy` is `wrangler deploy`), and a runtime clock or deploy time would change dates without content changes (FR-S17).
- **Alternatives**: `Date.now()` at module load (changes on every deploy and isolate); git commit dates (needs a build step).
