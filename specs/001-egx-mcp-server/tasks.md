# Tasks: EGX MCP Server

**Input**: Design documents from `specs/001-egx-mcp-server/`

**Prerequisites**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/), [quickstart.md](quickstart.md)

**Tests**: Required by the constitution (Development Workflow and Quality Gates): every MCP tool has contract tests, every scheduled job has tests for the holiday, empty-source and partial-failure cases. Tests run with Vitest 4.1.12 in the Workers pool (`@cloudflare/vitest-pool-workers` 0.23.0). Test tasks come first in each phase and must fail before their implementation tasks. The pool starts only after T127 (test compatibility date, owner decision D4); every acceptance that says a test file or `npm test` passes is checked after T127.

**Organization**: Tasks are grouped by user story. Build order follows the spec: P1 (US1, US2, US10), P2 (US3, US4), P3 (US5, US6, US7), P4 (US8, US9). The API key dashboard is built in Phase 2 because every story needs it; OAuth comes in US8.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: US1 to US10 from spec.md
- Paths are relative to the repository root (`D:\Work\EGX MCP`)

## Shared rules for every task

- Code follows the `code-quality` skill and the user's rules: no code comments, no em or en dashes in any text.
- D1 access only through `src/store/d1/*` and KV access only through `src/store/kv.ts`. Every D1 read selects explicit columns, uses prepared statements with bound parameters, and adds `meta.rows_read` to the request's rows-read counter (T030).
- Every provider `fetch` uses `AbortSignal.timeout(8000)` and the header `User-Agent: egx-mcp/1.0 (+https://github.com/ahmed-essawy/egx-mcp)`; failures throw `ProviderError` (T019).
- Every tool response uses the common envelope from [contracts/mcp-tools.md](contracts/mcp-tools.md#common-envelope) through `src/mcp/envelope.ts` (T018).
- Tool names are the exact names in [contracts/mcp-tools.md](contracts/mcp-tools.md) and [contracts/admin-tool.md](contracts/admin-tool.md), listed once in `src/mcp/tool-names.ts` (T031).
- Jobs collect their notices (`job_failed`, `new_listing`, `needs_ratio`, `fund_stale`, `source_switched`) in one list per run and write them with a single `raiseNotices` call (T022) at the end of the run, also when a step failed; `job_failed` is one notice per job, step and source with subject `<job>/<step>/<source>` and failed pages in `details.pages`, never one per page. Shared helpers called by several jobs (for example `syncListings` in `src/jobs/listing-sync.ts`) return their notices to the calling job and never call `raiseNotices` themselves (T103).
- Every personal table added later is deleted by `deleteAccount` and counted in `accountRowsUpperBound` (`src/store/d1/users.ts`) in the same task that creates it. Today the cascade covers `holdings`, `price_levels`, `api_keys`, `usage_daily` and `users`; T032 adds `usage_minute` if it runs.

## Implementation Strategy

### MVP first

1. Phase 1 and Phase 2 (stop at T007 if the probe needs a planner addendum).
2. US1, then validate quickstart Story 1 with an API key.
3. US2 and US10: the owner can deploy from the README and ask about any stock and the market.

### Incremental delivery

US3 (history, backfill over about 5 days), US4 (funds), then US5, US6, US7 (owner tools and ratios), then US8 (public OAuth) and US9 (gold and dollar), then Polish. The first public release is after US8, as the spec ships all stories in one release; earlier increments are deployed for the owner only.

## Notes

- `[P]` tasks touch different files and depend on no unfinished task.
- Every task's acceptance check must pass before the next dependent task starts.
- Planner addenda can be triggered only by T007 (EGX parser), T124 (CPU over budget) and T127 (test pool still not starting).
- Retention: the purges cover only `market_events` and `usage_daily`. `funds`, `nav_records`, `financial_figures` and `inflation_figures` are historical data and are never purged (constitution III). `notices` and `source_discrepancies` grow without a purge; a purge for them is decided later and has no task now.
